## 第 2 步：先让它"动起来"（完全不需要强化学习）

这一步是整个项目的地基。**如果你只学一样东西，学这个。**

### 2.1 只有 3 个概念

1. **关节角 `q`**：6 个数，6 个电机各转了多少弧度。`q = [0.0, -0.98, 2.06, -4.22, 1.57, 1.57]` 就是某个具体姿态。
2. **正运动学 FK（Forward Kinematics）**：**知道 6 个关节角 → 算出工具在哪**。
   这是纯几何：关节1转 θ₁ → link1 的位置和朝向 → 关节2转 θ₂ → … 一路乘变换矩阵到 link6，再加上铲斗的固定偏移。
   代码里就是这几行（`batched_env.py:72-84`）：

   ```python
   self._q(self.kinematic_state).copy_(requested)      # 把 6 个关节角塞进一个临时状态
   newton.eval_fk(self.model, ...)                     # Newton 做 FK
   return self._tcp(self.kinematic_state).clone()      # 读出 link6 位姿 + 固定偏移 = TCP
   ```

   **`eval_fk` 就是"算一下但不推进物理"**。你给它关节角，它告诉你铲斗在哪，仅此而已。

3. **TCP（Tool Center Point）**：工具的"工作点"。本项目里不是法兰中心，而是**铲斗前缘的中点**。它是一个预计算的常量偏移：

   ```python
   TCP_OFFSET_LINK6 = np.array([-0.025, -0.719, -0.00047661], dtype=np.float32)
   ```
   `reach_env.py:20`

   TCP 世界坐标 = link6 的位置 + 把上面这个偏移按 link6 的姿态旋转一下。

> 这三个概念就是"机械臂版的刚体变换"。如果你能看懂 `p_world = p_link6 + R_link6 · offset`，这一步就过了。

### 2.2 PD 控制：机械臂为什么会"听话地转过去"

你给机械臂 6 个**目标关节角**，它怎么动过去？靠一个叫 PD（比例-微分）的控制器：

```text
力矩 = kp × (目标角 - 当前角) - kd × 当前角速度
```

- `kp × 误差` 是**弹簧**：离目标越远，拉得越用力
- `- kd × 速度` 是**阻尼**：动得越快，刹车越狠，防止来回振荡

本项目 `kp = 1200`, `kd = 80`（`scene_builder.py:31-32`）。你写进 `control.joint_target_pos`，MuJoCo 求解器内部就把这个 PD 算成力矩。

**核心动作逻辑只有 3 行**（`batched_env.py:114-117`）：

```python
bounded = actions.clamp(-1.0, 1.0)                                    # 动作裁到 [-1,1]
targets = (joint_position + bounded * 0.04).clamp(lower, upper)       # 目标 = 当前 + 最多 0.04 rad
control.joint_target_pos = targets                                    # 交给 PD
```

**读懂这 3 行，你就读懂了"机械臂如何被控制"**：

- 策略不直接给力矩，给的是"关节目标位置"
- 每个控制周期（0.05 秒）目标最多挪动 0.04 弧度（约 2.3°）→ 天然限速
- 目标一定被裁进关节限位 → **不可能因为策略发疯而越界**

> ⚠️ **一个必须知道的坑**：纯 PD 在重力下有**稳态误差**。铲斗又长又重，PD 会永远停在离目标差一点的地方。代码注释里写得很直白—— oracle 控制器的增益必须设成 `2.0` 才能压平这个误差：

```python
# A gain above one compensates the position-drive steady-state error
# caused by gravity acting through the long scoop.
return np.clip(2.0 * error / self.config.action_scale_rad, -1.0, 1.0)
```
`reach_task.py:103-106`

**这是一个绝佳的教学点**：静态 PD 压不平的误差，需要"过冲一点再回来"的**时序行为**才能压平 —— 而这正是神经网络策略能做、而简单控制器做不到的事。这就是为什么这里需要 RL。

## 第 3 步：把"动"包装成一个游戏

现在你有了一个"能动的机械臂"。接下来要把它变成一个**可以反复试错、有输赢的游戏**。

### 3.1 游戏的四件套

任何强化学习问题都是这四件事，用打游戏类比：

| 概念 | 游戏里 | 本项目 |
| --- | --- | --- |
| **observation（观测）** | 屏幕像素 | **22 个浮点数** |
| **action（动作）** | 按键 | **6 个 [-1,1] 的数** |
| **reward（奖励）** | 得分 | 一个浮点数 |
| **reset / episode（重置/回合）** | 死了重开一局 | 250 步（12.5 秒）后重开 |

### 3.2 Observation：这 22 个数为什么是这 22 个

| 段 | 宽度 | 内容 | 如果**缺了**会怎样 |
| --- | ---: | --- | --- |
| `q_normalized` | 6 | 各关节角归一化到约 [-1,1] | 策略不知道自己的手臂现在什么姿势 → 完全没法决策 |
| `qd_normalized` | 6 | 各关节速度 / 2.0，裁到 [-1,1] | 策略不知道自己在往哪冲 → 无法学会"提前刹车"，动作会抖 |
| `tcp_to_goal` | 3 | `目标 - TCP`，单位 m | 策略不知道目标在哪 → 没法决策 |
| `previous_action` | 6 | 上一个动作 | 策略不知道自己上一步命令了什么 → 动作会突变、来回抖 |
| `distance_to_goal` | 1 | TCP 到目标的距离，单位 m | 少了一个"离成功还有多远"的标量，学习会慢很多 |

**这个设计思路值得学**：它不是"把能给的都给"，而是**每一项都有明确的决策用途**。

看代码（这是最清晰的一份）：

```python
q_normalized  = 2.0 * (q - lower) / (upper - lower) - 1.0
qd_normalized = np.clip(qd / config.max_joint_speed_rad_s, -1.0, 1.0)
tcp_to_goal   = goal - tcp
distance      = np.asarray([np.linalg.norm(tcp_to_goal)], dtype=np.float32)
return np.concatenate((q_normalized, qd_normalized, tcp_to_goal, last_action, distance))
```
`reach_contract.py:53-57`

> **归一化为什么重要**：不同关节的限位不同（joint3 只有 ±2.79，joint1 有 ±6.28），如果不归一化，同样转 1 弧度在不同关节上"意义"差很多，神经网络很难学。归一化后每个数都在 [-1,1] 附近，网络更容易拟合。

### 3.3 Action：为什么是"增量"而不是"绝对角度"

```text
q_target = clamp(q_current + action × 0.04 rad, joint_lower, joint_upper)
```

- **增量式（相对当前姿态）**的好处：策略只需要学"往哪个方向微调"，不用学"绝对该在哪"。这让学习难度下降一个量级。
- **绝对角度式**的问题：策略必须学会把手臂从任意初始姿态精确插值到目标姿态，稍偏一点就抖动。
- `0.04 rad` 上限 = 天然的**速度限制**（20 Hz 下最大 0.8 rad/s，远低于 URDF 的 2.6–4.5 rad/s）。这是安全边界，不是性能妥协。

### 3.4 Reward：为什么不能"到了给 1 分，没到给 0 分"

这是强化学习最反直觉、也最重要的一点。

假设奖励只有"距离 < 3 cm 给 +10，否则 0"。那么策略随机乱动 250 步，**几乎永远碰不到那 3 cm 的球** → 从头到尾奖励全是 0 → 没有任何"哪个动作更好"的信息 → **学不动**。这叫"稀疏奖励"问题。

所以这里用了**密集奖励**：

```python
progress = previous_distance - distance                          # 这一步靠近了多少
rewards  = 2.0 * progress                                        # ← 每靠近一点都有正反馈
         - 0.2 * distance                                        # ← 没进步时也偏好靠近
         - 0.01 * mean(action^2)                                 # ← 偏好平稳动作
         + 10.0 * (distance <= 0.03)                             # ← 成功大奖
```
`rsl_rl_env.py:190-194`

| 项 | 作用 | 类比 |
| --- | --- | --- |
| `2.0 × progress` | 主要学习信号 | "每靠近一步给一点分" —— 让随机探索也有梯度 |
| `-0.2 × distance` | 兜底偏好 | "站着不动也别离太远" |
| `-0.01 × action²` | 正则化 | "别抖" |
| `+10.0` 成功 | 明确目标 | "赢了大奖" |

> **一个诚实的事实**：契约里写的 `-5.0` 失败惩罚（`docs/task_contract.md:37`）**当前从来没生效过**。因为 Reach-v0 把接触检测关掉了（`disable_contacts=True`），而且动作被裁在限位内，所以"违反安全条件"永远不发生。等 Gate 3 引入障碍物才会真正用上。

### 3.5 Reset 与目标采样：为什么要"费劲地"用 FK 生成目标

最朴素的想法：在机械臂前面框一个长方体，在里面随便撒点当目标。**这是错的**，因为长方体里很多点机械臂根本够不到 → 策略对着一堆"不可能的任务"被扣分 → 学不好。

所以这里用了很聪明的一招（`rsl_rl_env.py:117-156`）：

```text
重复最多 256 次：
    ① 在当前关节角附近随机扰动，得到一个候选关节姿态 q_candidate
       （扰动上限 SAFE_GOAL_DELTA_RAD = [0.30, 0.25, 0.25, 0.20, 0.20, 0.20]）
    ② 用 FK 算出这个姿态下 TCP 会在哪  ← 关键：用 FK，不是猜
    ③ 如果它离起点的距离落在我想要的区间内 → 接受
    ④ 否则重试
```

**结果：每一个目标都天然存在一个合法的关节解**，策略学的是"解决一类可达问题"，而不是"记住一条轨迹"或被"不可达目标"污染奖励。

Gate 2F 又加了两层：
- **随机起点**：`SAFE_START_DELTA_RAD = [0.20, 0.18, 0.18, 0.12, 0.12, 0.12]`，每回合起始姿态在标称姿态附近随机（`rsl_rl_env.py:88-95`）
- **距离分层**：目标距离分成 near 0.10–0.20 / medium 0.20–0.32 / far 0.32–0.45 三层**均衡采样**（`rsl_rl_env.py:18-22, 97-115`）

为什么要分层？因为如果只在 easy 层训练，成功率 100% 是假象；分层后每一层都单独统计成功率，才能说"这策略在远距离也真的行"。

## 第 4 步：PPO 到底做了什么改动

现在你有了一个"游戏"。问题是：谁来玩？

### 4.1 玩家其实是一个函数

```text
策略网络 = 一个函数 f：R²² → R⁶
           输入：22 个观测
           输出：6 个动作（每个都在 [-1,1]）

网络结构：22 → 64 → 64 → 6，激活函数 ELU
参数量 ：(22×64+64) + (64×64+64) + (64×6+6) ≈ 6000 个
```
`train_reach.py:36-46`

**就这么小。** 整个项目的"智能"就是 6000 个浮点数。所谓的"训练"，就是把这 6000 个数调到合适的位置。

### 4.2 训练循环：试 → 记 → 改

```text
重复 400 次（这里叫"迭代"/iteration）：
  ┌─ 试（采样）─────────────────────────────────
  │  对 64 个并行环境，各跑 24 步：
  │     action = 网络(obs) + 随机噪声          ← 注意"加噪声"，这是探索
  │     obs, reward, done = env.step(action)   ← 环境返回下一局面和得分
  │     把 (obs, action, reward, ...) 记进一个大表格
  │
  ├─ 算（评估好坏）───────────────────────────
  │  用这套数据反推："每个动作比平均水平好多少"（这叫作 advantage）
  │
  └─ 改（更新参数）───────────────────────────
     梯度下降 5 轮 × 4 个小批：
       好动作 → 提高它的概率
       坏动作 → 降低它的概率
       但限制：新网络不许跟旧网络差太多 ← 这是 PPO 的核心
```

### 4.3 三个必须懂的设计决定

**① 为什么输出要加噪声？**
如果网络输出什么就执行什么，那它永远只在当前"想法"附近打转，探索不到更好的可能。所以训练时输出的是**高斯分布的采样**，网络给的是**均值**，标准差是一个可学习参数（初始 0.8）：

```python
"distribution_cfg": {"class_name": "GaussianDistribution", "init_std": 0.8, "std_type": "scalar"}
```
`train_reach.py:41-45`

**② 为什么需要 64 个并行环境？**
一次物理试验只产生"一个动作 → 一个奖励"这么点信息，太慢了。64 个环境同时跑，一次迭代就有 `64 × 24 = 1536` 个样本。400 次迭代 = **614,400 个交互样本**。

关键：这 64 个环境在 GPU 上是**批量张量运算**，不是 64 个 Python 循环。这就是 `batched_env.py` 存在的唯一理由。

**③ 为什么"超时"要单独标记？**
回合结束有两种情况：**成功**（真终局）和**数到 250 步**（截断）。如果混为一谈，网络会以为"第 250 步是个坏结局"，从而害怕靠近目标。所以要单独用 `time_outs` 标出来：

```python
extras = {"time_outs": time_outs, "successes": successes, "distance": distance}
```
`rsl_rl_env.py:205-209`

RSL-RL 收到这个标记后，会用地道的写法给这一步"补上未来的价值"（自举）：

```python
# Bootstrapping on time outs
if "time_outs" in extras:
    self.transition.rewards += self.gamma * torch.squeeze(
        self.transition.values * extras["time_outs"].unsqueeze(1).to(self.device), 1)
```
`rsl_rl/algorithms/ppo.py:174-179`

**你不需要懂 PPO 的数学，但需要知道这个约定存在**，因为你自己写环境时必须提供它。

### 4.4 为什么要接 RSL-RL 这个库

`rsl_rl_env.py` 里你只需要实现 4 个东西，剩下全部交给库：

| 你要提供 | 作用 |
| --- | --- |
| `get_observations()` | 返回 22 个数（包成 `TensorDict`） |
| `step(actions)` | 吃 6 个数，走物理，返回新观测 + 奖励 + 是否结束 |
| `num_envs` / `num_actions` / `max_episode_length` | 三个类属性 |
| `episode_length_buf` | 记录每个环境已经跑了多少步 |

`step()` 里最后一行（`rsl_rl_env.py:220`）：

```python
return self.get_observations(), rewards, dones.to(dtype=torch.long), extras
```

**这四个返回值的顺序和类型就是你和 RSL-RL 之间的合同**。读懂这行，你就理解了整个适配层。

### 4.5 这一步要补的知识

| 知识点 | 为什么需要 | 推荐 |
| --- | --- | --- |
| 策略梯度 / 为什么要"提高好动作的概率" | 理解 4.2 的"改"步骤 | [Spinning Up: PPO](https://spinningup.openai.com/en/latest/algorithms/ppo.html) —— **只读 Quick Facts 和开头的直觉解释** |
| advantage、GAE、折扣因子 γ | 理解"比平均水平好多少" | 同上；不要推公式 |
| PPO 的 clip（为什么限制更新幅度） | 理解"不许跟旧网络差太多" | 同上，看那句 $\min(r A, \text{clip}(r, 1-\epsilon, 1+\epsilon) A)$ 的**直觉**即可 |
| 熵正则化 entropy | 理解 `entropy_coef: 0.005` 是"保持探索" | 同上 |
| 自适应学习率（按 KL 调 lr） | 理解 `desired_kl: 0.01` | 同上，可选 |

> **不要做的事**：不要一开始就去手推 PPO 的完整公式、不要横向比较 SAC/TD3、不要读 CS285 全套。这些都可以等 Gate 3/4 之后。`学习路径与资料.md` 里明确列了"暂时不要学的内容"。

## 第 5 步：训练循环 vs 部署循环（全项目最关键的对照）

**这一个对照表，是理解"训练结果如何驱动机械臂"的钥匙。**

```text
┌───── 训练循环（跑 400 次迭代，每次 24 步 × 64 环境）──────────────┐
│                                                                    │
│  ① obs  = 22 个数（读 q/qd/TCP + 目标）                           │
│  ② a    = 网络(obs) + 噪声        ← 有随机探索                     │
│  ③ q_t  = clamp(q + a×0.04, 限位)                                  │
│  ④ Newton 前进 0.05 s（4 个物理子步）                              │
│  ⑤ r    = 2×progress - 0.2×d - 0.01×a² + 10×成功  ← 有奖励         │
│  ⑥ 记进大表格；多次之后        ← ★ 更新网络参数（梯度下降）        │
│  ⑦ 成功或 250 步 → 重新采样起点和目标，重开                        │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘

┌───── 部署循环（每个控制周期跑一次，永远不停）──────────────────────┐
│                                                                    │
│  ① obs  = 22 个数（读 q/qd/TCP + 目标）        ← 完全一样          │
│  ② a    = 网络(obs)               ← ★ 去掉噪声，确定性输出        │
│  ③ q_t  = clamp(q + a×0.04, 限位)             ← 完全一样          │
│  ④ Newton 前进 0.05 s（4 个物理子步）         ← 真机换成伺服       │
│  ⑤ d    = ‖goal - tcp‖  ← 只算距离，不算奖励  ← ★ 不再需要奖励    │
│  ⑥ 不更新任何参数             ← ★ 网络冻结                        │
│  ⑦ 距离 < 0.03 → 换下一个目标                  ← 上层任务系统给    │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**只有 3 个 `★` 的区别**：去掉探索噪声、不再算/用奖励、不再更新参数。其余完全一致。

**这就是为什么 `docs/task_contract.md` 说"训练、回放和未来真机必须使用完全相同的观测顺序、单位和动作缩放"** —— 因为这个循环一旦有一处不一致，网络看到的"世界"就变了，它学的东西立刻失效。

### 5.1 部署时网络变成了什么

导出时，RSL-RL 把 actor 包装成一个"只吃张量、只吐张量"的模块：

```python
def forward(self, x: torch.Tensor) -> torch.Tensor:
    x = self.obs_normalizer(x)
    out = self.mlp(x)
    return self.deterministic_output(out)
```
`rsl_rl/models/mlp_model.py:210-214`

两个关键点：

1. **输入是裸张量，不是 TensorDict**。所以回放代码里必须传 `env._observations_tensor()`，不能传 `env.get_observations()`：

   ```python
   action = self.policy(self.env._observations_tensor())
   _, _, dones, extras = self.env.step(action, auto_reset=False)
   ```
   `play_random_policy.py:75-76`

2. **输出是确定性的**。因为 `std_type="scalar"` 时，`deterministic_output()` 就是"原样返回 MLP 输出"，也就是**高斯分布的均值**：

   ```python
   def deterministic_output(self, mlp_output: torch.Tensor) -> torch.Tensor:
       """Extract the mean from the MLP output."""
       return mlp_output
   ```
   `rsl_rl/modules/distribution.py:182-184`

   → **同一个观测一定得到同一个动作，可复现**。这对真机安全是必需的。

### 5.2 三个产物，别搞混

| 文件 | 内容 | 什么时候用 |
| --- | --- | --- |
| `model_400.pt`（153 KB） | actor + critic + optimizer + 迭代号 | **续训**、微调 |
| `exported/policy.pt`（35 KB） | **只有 actor 的前向计算** | **执行/回放/评估** ← 你关心的就是这个 |
| `exported/policy.onnx`（31 KB） | 同一张图的 ONNX | 脱离 PyTorch 部署（C++/TensorRT） |

`model_400.pt` 是 `policy.pt` 的 4 倍大，因为多了 critic 和 Adam 优化器的动量状态。**部署时只需要 35 KB 那个**。

## 第 8 步：五个最容易困惑的问题

### Q1：为什么不直接解 IK（逆运动学），非要用 RL？

因为**IK 只解决"静态的一步"，不解决"随时间的过程"**：

- IK 回答："要让铲斗到这个位姿，关节角该是多少？"
- 但实际问题是：姿态会漂移、PD 有重力稳态误差、手臂运动有惯量、以后还有沙子的阻力和碰撞。
- RL 学的是**一个带反馈的连续控制策略**：每一帧根据当前真实状态修正。这是 IK 给不了的。
- 而且这个项目的目的**不是**解决"到达"本身——到达只是用来**验证整条 RL 管道是通的**。后面挖沙（Gate 4/5）根本不存在解析解。

### Q2：为什么目标要用 FK 生成，而不是直接框一个长方体？

见 3.5 节。简短版：如果目标落在机械臂够不到的地方，策略会被"不可能完成的任务"扣分，学到的全是噪声。用 FK 生成保证每个目标都可达。

### Q3：PD 有稳态误差，为什么策略还能成功？

因为策略学的不是"静态地把目标角设到某处"，而是**一段时间内的动作序列**。它可以学会"稍微过冲一点、利用手臂的弹性停在正确位置"这种**动态补偿**行为。这是静态控制器（比如 `reach_task.py` 里那个 oracle）需要把增益调到 2.0 才能勉强做到、而神经网络可以自动学出来的东西。

再加上 3 cm 的成功阈值给了容差。

### Q4：三层评估都 100/100，为什么还不能上真机？

因为仿真里**没有**这些东西（按 `roadmap.md` 的 Gate 6）：

| 仿真里有的 | 真机上还缺的 |
| --- | --- |
| 无接触（`disable_contacts=True`） | 碰撞、摩擦、抓取 |
| 确定的参数（kp=1200, kd=80） | 伺服增益未辨识、负载质量未标定（铲斗 1 kg 是暂定值） |
| 没有传感器噪声、没有通信延迟 | 编码器噪声、控制周期抖动 |
| 关节限位自动 clamp | 需要在策略外做软限位、速度/力矩钳制、工作空间盒、急停 |
| 训练分布只有距起点 0.10–0.45 m | 真实工作空间更大，且未测过 |

**核心认知：`policy.pt` 只是一个 22→6 的函数，它没有任何安全能力。** 安全必须在它外面实现。

### Q5：为什么要给 22 个数？少给几个不行吗？

见 3.2 节的表格——每一项都有明确的决策用途，去掉哪一项都会让策略"瞎掉一部分"。这是**观测设计**（observation design），是 RL 里最需要工程判断、也最能影响成败的部分。

> ⚠️ **一个必须提前知道的记号差异**
>
> 这本书用**旋量 / 指数积（Product of Exponentials, PoE）** 写正运动学：
> $$T(\theta) = e^{[S_1]\theta_1} e^{[S_2]\theta_2} \cdots e^{[S_n]\theta_n} M$$
>
> 而本项目的 URDF 用的是**链式**写法（每个关节一个 4×4）：
> $$T = \prod_{i=1}^{6} \underbrace{\text{Translate}(p_i) \cdot \text{RPY}(r_i)}_{\text{关节坐标系}} \cdot \underbrace{\text{Rot}(\text{axis}_i, q_i)}_{\text{绕轴转}}$$
>
> **两者描述的是同一件事**，都是"一串 4×4 刚体变换连乘"，只是记号不同。URDF 的写法更直观。
>
> 所以读 Ch.4 的目标**不是**"学会手算 FK"（本项目由 `newton.eval_fk()` 负责算），而是理解这个映射的**性质**：
> q → 位姿是**唯一、连续、好算**的，但**不可逆**（IK 难、可能无解、可能多解）——这正是为什么本项目用 FK 反向生成目标（第 3.5 节）。
>
> **明确跳过**：Ch.5（速度/雅可比）、Ch.6（逆运动学）、Ch.7、Ch.8（动力学）、Ch.9、Ch.10、Ch.11（控制，等 Gate 6 接真机再看）、Ch.12、Ch.13、附录 C（DH 参数，又一种记号）。
